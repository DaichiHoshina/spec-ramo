# Design Doc の書き方の規範

`/specramo:design` が本文を組む前に読む規範。Design Doc を設計の説明ではなく、実装と検証の入力として記載する。

## 逆算の 4 原則

1. **完了の定義から始める**: 「実装が終わった」と言える条件 (受け入れ条件) を先に表で並べる。条件に `AC-1` のような ID を振らない。後続のステップから条件を指すときは、原文の文で引用する。PRD の条件は PRD の番号で参照し (番号が無ければ条件の文で引用する)、Design Doc には PRD に無い条件だけを記載する。本文はこの条件を満たすための説明として記載し、どの条件にも対応しない節は削る
2. **実装者が迷う点だけ決める**: データ / API / 画面 / 権限 / 失敗時 / 移行 のうち、実装者が code を読んでも決められない点を「決定事項」に記載する。実装の書き方 (層の分け方 / 関数名 / 読み込み済みの再利用) は含めない
3. **検証できない仕様は記載しない**: 受け入れ条件は「〜のとき、〜が〜になる」の形で、test か手動の確認で真偽が決まる文にする。「適切に」「必要に応じて」を使わない
4. **後続のステップへ渡せる形にする**: `/specramo:plan` が受け入れ条件を文の引用で Phase に割り当て、`/specramo:implement` が完了報告で満たした条件を返し、`/specramo:review` が条件ごとに実装と test の有無を照合する。条件の総数と本文の説明が一致していることを、完成前に確かめる

## 利用者が仕様を理解できる文章

読み手は実装者だけでなく、機能を決める利用者本人でもある。

- **振る舞いは「誰が / 何をすると / どうなる」の形にする**: 主語を利用者か system の具体名にし、1 文に 1 つの結果だけを記載する (例: 「管理者が在庫を 0 にすると、商品一覧はその商品を表示しない」)
- **識別子を本文から除く**: table 名 / column 名 / endpoint / class 名は「決定事項」の表と Appendix にまとめ、振る舞いの説明には日本語の名前を使う
- **用語は初出で説明する**: 略語と社内用語は「用語」節で 1 行ずつ定義し、本文では定義した語だけを使う
- **前提、結果の順に並べる**: 条件が複数あるときは、条件を先に並べてから結果を記載する。例外や境界 (0 件 / 上限 / 同時実行 / 再送) は、通常の振る舞いの直後に下位の 箇条書き で置く
- **段落より箇条書き**: 振る舞いと決定事項は 箇条書き と字下げで並べ、段落は採用理由の説明だけに使う

## 文書全体の読みやすさ (構造ゲート)

本文の前に見出しを決め、見出しごとに役割と所有する主張を決める。文や単語を修正する前に、見出しと各段落の主張だけを追い、次の 6 点を確かめる。

1. **読む目的を 1 つにする**: 調査記録、意思決定、実装手順のように、読後の行動が変わる内容は文書を分ける
2. **結論の置き場所を 1 つにする**: 結論と理由を所有する節を決める。概要は結論を探す入口にとどめ、別の節の説明を言い換えて繰り返さない
3. **同じ問いへの選択肢を比べる**: 候補は同じ決定対象に答える形へそろえる。複数の独立した判断を 1 つの案にまとめず、判断ごとに分ける
4. **現在の状態を記載する**: 完成稿には現在の事実と判断を記載し、執筆中の訂正や調査の順序を含めない。不採用の理由や判断に必要な前提の変更は、証拠なので記載する
5. **同じ対象を同じ用語で呼ぶ**: 同じ対象を意図なく言い換えない。似た語が別の状態や対象を指すときは、冒頭で違いを定義する
6. **因果を順に追える形にする**: 主体、条件、原因、結果の対応が一度で追えない箇所だけ、文や段落を分ける

字数、文数、節の数は、この確認の合否に使わない。

## 文章の自己点検 (書き出した後)

次の 5 項目を当て、当たった箇所だけを書き換える。事実、時制、因果関係、主体は変えない。

1. 各節の最初の文が、その節の結論になっている
2. 1 文に論点が 1 つだけある
3. 「適切に」「必要に応じて」「柔軟に」のような、判定できない語を使っていない
4. 同じ対象を、節ごとに別の語で呼んでいない
5. 入力や確かめた資料に無い数値・事例・理由を作っていない
