# /specramo:design の細則 (入力の分岐 / Step 3 / 3.5 / 4 / 5 / 7.6 と完了判定の判定方法)

`SKILL.md` の各 Step から読む。規則の中身は SKILL.md 本文と同じで、本文には手順の骨格だけを置いている。

## update mode

- `--update <path>` 相当。
- 既存の受け入れ条件の文を保ち、差分だけ Edit する。
- この skill の定義を更新した後の既存 Design Doc も再生成せず、`bash "${CLAUDE_PLUGIN_ROOT}/scripts/dd-gate.sh" <path>` を適用して FAIL と WARN の項目だけ Edit する。
- 起動するのは仕様が変わったときだけで、実装中に決まった細部を都度書き戻して仕様書にしない (書き換えたら user がレビュー依頼して認識を合わせる)

## derive mode

- PRD から導く。
- PRD の `1.5 decision rationale` (Q1-Q5) は再評価せず転記する (`Source: <PRD path>` を付ける)。
- PRD の `1.6 Non-Goals` は参照だけにし、DD の Non-Goals には PRD に無い対象外 (技術的な入口の除外など) だけを記載する。
- PRD に実装方式 (列 / 制約 / SQL) が含まれていても、それは転記の対象でなく候補の 1 つとして扱い、Step 3 で先例と比べてから決める。
- 同じ dir に `/specramo:prd` が分けた技術メモ (tech-notes.md) があれば Step 3 の入力として Read する。
- 記載された code の位置と先例は、書かれた時点の事実として実物で確かめてから使う

## Step 3: Analyze code の論点

既存の振る舞いと影響範囲を確かめる。Serena などの code 解析 tool があれば使い、無ければ grep で調べる。最初に実装済みかを確かめ、そのあと論点ごとに次を確かめる:

- **実装済みの確認 (最初に行う)**: 要件に登場する機能名・画面名・出力の名前を語にして `git grep -l` を実行する。要件がすでに実装されていれば、Design Doc を書かず、実物の場所 (file と行) を報告して止まる。一部だけ実装済みなら、未実装の差分だけを対象にする
- **先例の数え方**: schema / API / 命名の決定ごとに repo の先例を数える (例: 同じ役割の名前の付け方、識別子の一意性の範囲、入れ子の一覧を親の応答に同梱するか別 endpoint にするか)。定義 file (schema / 型定義 / 設定) を grep して「候補 A n 件 / 候補 B m 件」を出し、多数派を基本の案にする (外れるときだけ決定事項に理由を記載)。先例は規範に無い慣行を取り込むためのもので、多数派が常に正しいわけではない (user の判断で覆せる)。「現状こうなっている」は実物で裏取りし、推測には【要確認】を付ける
- **先例は現在の状態で数える**: 変更を追加した回数でなく、現在の定義で数える。後から撤回された形 (後の変更が制約を削除し、別の制約に置き換えたもの) は先例に数えず、撤回した理由を却下案の根拠に使う。先例が 0 件の案を採るときは、多数派の案を却下する理由を code の根拠で決定事項に記載する。記載できないなら多数派の案を採る
- **同時実行の競合の防ぎ方**: 一意性をどこで守るかを決めるときは、制約を維持する案も含めて、先に登録する経路が既存のロック (行ロック、同じ対象への更新 等) で直列化されているかを確かめる。確かめた経路と行は、不変条件の担い手の表に記載する。直列化されていれば「制約を持たず、読み取りの条件と既存のロックで守る」案を候補に加え、「アプリ側の判定が必要になる」をその案の却下理由に使わない。直列化されていなければ、同じ業務キー (親の行) をロックする既存のトランザクションを探す。見つかれば「登録をそのトランザクションの内側で実行し、そのロックで守る」案を候補に加える。今の制約を維持する案を採るときは、その制約が業務の流れ (削除した後の再作成、別の値での選び直し) を妨げないかを受け入れ条件で確かめる
- **既存 endpoint 拡張時**: 現状の error 応答の形 (validation 違反の HTTP status と body) を Current State に書き、Appendix B で変えるなら「既存挙動の変更」として受け入れ条件 5.1 へ記載する。拡張する業務処理の層を共有する別の入口 (CSV 一括更新 等) を列挙し、新しい制約がそこにも適用されるなら Non-Goals の入口か受け入れ条件に記載する
- **保存先 / endpoint の実在確認**: 保存先の項目と制約 (必須 / 一意 / 参照) は API の validate から推定せず、定義 file で確かめる。Implementation Surface へ記載する endpoint は route 定義 (framework の routing 定義) で実在を確かめ、無いものは「新規」、1 件取得と一覧のような形の違いは実物の形で書く

## Step 3.5: 骨子の内容と待ち方

draft 前に `writing-rules.md` の「文書全体の読みやすさ」を当て、見出しの役割と所有する主張を決める。

- **骨子の内容**: template の項目ごとの記載する / 記載しない と理由 1 行、各節の主張 1 行、Implementation Surface の合計 (数と新規・既存拡張の別。endpoint は route で確認できたもの。table は新規 / 列追加の別と一意制約の範囲まで)、受け入れ条件の件数 (PRD 書き戻し / DD の境界)、決定事項の見出しと却下案、Non-Goals、未確定事項と確認先。user の判断が必要な項目にも推奨を記載しておき、問いは投げない。箇条書きと表だけで出し、文体は整えない
- **待ち方**: 骨子を 1 画面で chat に示し、user の差分を待ってから本文へ進む (骨子を決めずに本文から着手すると、書き直しが繰り返し発生する)。user は差分だけ返し、「OK」なら本文に入る
- **待てない場合の代替**: user の返答を待てない context (非対話の実行、別 session からの依頼) では推奨のまま本文に進み、骨子と「未確認のまま進んだ」旨を DD 冒頭の注記 (blockquote) に記載して user が後から差分を返せるようにする

## Step 4: 受け入れ条件の表の書き方

- 先頭の `No` 列の通し番号は読みやすさのためだけで、本文や後続のステップから引用しない
- 列名を `#` にしない (GitHub が番号を issue への link にするので紛らわしくなる)
- PRD の条件は PRD の番号 (A-n など) で参照する。`/specramo:prd` で作った PRD のように番号が無ければ条件の文を backtick で引用する
- DD には PRD に無い条件だけを記載する

## Step 5: 決定事項の 3 論点と節の削り方

決定事項では次の 3 論点を毎回検討する。複数案が実際にあったものだけ小見出しで記載し、自明なものは表に 1 行で記録する (4 箇条書き の小見出しを一律に増やさない):

1. 他 context の master を参照するか独自に格納するか (Step 3 で、repo に context 間の依存を制限する lint 設定があるかを確かめる)
2. 既存 endpoint の拡張か新設か (却下案を 1 つ以上)
3. 1:N の入力を平坦な形式 (CSV / 一括 API) でどう表すか (登録と更新の両方。更新側を対象外にするなら Non-Goals に入口を記載する)

節の削り方:

- 決定を追加する・変えるたびに Implementation Surface へ戻り、その決定で増える endpoint / Read / Write / 画面 / table を表と合計 1 行へ追加する
- 各節は「どの受け入れ条件を満たすための説明か」を書き手が答えられる状態にし、どの条件にも対応しない節は削る
- 見出しや決定事項に条件の番号を引用しない
- repo の DD template があっても、記載することの無い節は作らない

## Step 7.6: 第三者 review の実行者と指摘の扱い

Design Doc はチームでレビューするので、内容を知らない読み手が理解できるかを確かめる。観点は 6 つ (主語・目的語の曖昧さ / 前提知識への依存 / 因果関係の不成立 / 曖昧な動詞 / 具体を含まない印象語 / 元実装から読み取れない断定)。

- **実行者**: 書き手と別の context にするため、Claude Code の汎用のサブエージェントへ委譲する。prompt は「内容を知らない読み手として `<DD path>` を読み、上の 6 観点で問題箇所を挙げる。元実装の照合先は `<repo root>`。書き直さず、指摘の list だけを返す」とする。書き手の context で読むと、知っている前提を補って読むので第三者の視点にならない
- **指摘の扱い**: 「前提知識への依存」と「元実装から読み取れない断定」は Edit で修正する (用語を 1 行で定義する / code で確かめて断定を書き換えるか【要確認】を付ける)。他の 4 観点は、読み違えの原因になるものだけ修正する。修正しなかった指摘は理由を 1 行添えて chat に並べ、user が判断する
- 再 review はしない (1 回だけ)。`--dry` では draft text を対象にする

## 完了判定 #3: 対象範囲の判定方法

- Implementation Surface の合計 1 行と 5 表を置く。Current State の直後に置き、endpoint 名と画面名と table 名 (RDB 以外は保存単位の名前) で記載する。保存データの変更が無いときも Data Schema に「保存データの変更なし」の 1 行を置く
- **見出し名と 1 列目の header は雛形のとおりに記載する**。`### Backend API` の 1 列目は `endpoint`、`### Frontend` の 1 列目は `画面` で、能力の 2 表は `### Required Read Capabilities` と `### Required Write Capabilities` にする。`dd-gate.sh` はこの見出しと header で表を特定するので、`### API` や `### 画面` のように言い換えると表 0 行と判定される
- 合計 1 行の各数は表の行を `grep -c` で数えて書く (header 行と区切り行を除く。列名の「新規 / 既存」が hit に含まれる)
- `Read n / Write n` が指すのは Backend API 表の種別列の内訳で、能力の表の行数は「Read の能力 n」のように別の語で書き、合計 1 行では API の内訳より後ろに並べる (`dd-gate.sh` は最初に現れた `Read n` を採用する)
- Frontend 表の行は変更がある画面だけにし、画面の変更が無いときは表を作らない (合計 1 行には「画面 0」と記載するか、画面の数を省く。Data Schema の「保存データの変更なし」と違い、「変更なし」の行を追加すると合計と行数が一致しない)
- Web API も画面も無い変更 (CLI / library / batch / 組み込み 等) は Backend API と Frontend の表を作らず、外部 interface を `### Interfaces` 表 (`| interface | 種類 (CLI / 公開 API / event / batch / 設定 等) | 変更 (新規 / 既存拡張) | 主な責務 |`) に記載し、合計 1 行では「interface n」と数える。`dd-gate.sh` は表も合計の数も無い項目を対象なしとして PASS にする
- endpoint の新規 / 既存拡張と形 (1 件取得 / 一覧) が route 定義と一致する

## 完了判定 #11: 実装方法に寄りすぎていないかの判定方法

- **script 検出方法**: 受け入れ条件 / 振る舞い / 決定事項の節を grep し、backtick / path / 拡張子付きの file 名 / HTTP status の hit が 0
- **許可される記載範囲**: Implementation Surface には endpoint 名と画面名と table / column 名 (Data Schema の 5 列表)、Appendix B には field / HTTP status を記載してよい
- **禁止対象**: file path / 関数名 / SQL / DDL 全文はどこにも記載しない (一覧は具体名、判断は抽象)
