# /specramo:phase-design の細則 (Step 0 / 1 / 2 / 3 / 4 と禁止事項の判定方法)

`skills/phase-design/SKILL.md` の各 Step から読む。規則の中身は SKILL.md 本文と同じで、本文には手順の骨格だけを置いている。

## なぜ作業計画書と分けるか

作業計画書には全 Phase 分が着手前に集まる。実装形まで記載すると、着手しない Phase の操作名と問い合わせまで読むことになる。作業計画書は「どの責務を、どの単位・順序で」の地図に保ち、実装形は着手する Phase の分だけ Phase 詳細設計に格納する。

**分離の効果は限定的、行数削減は期待しない。**

- 作業計画書の中で実装形にあたる部分は、全体の 1 割程度にとどまる
- 効果は「着手する Phase 以外の実装形を読まずに済む」点と、次の段落の手戻りの防止になる

操作名・問い合わせ・呼び出し元は既存 code を確かめないと妥当な形が決まらない。上流で決め打ちすると、調査結果と一致しなかったときに作業計画書ごと書き換えることになるので、Phase に着手する直前に決める。

## Step 0: 省略判定の考え方

- **原則は書かない判断にする**。器があると埋めたくなるが、埋める価値の無い Phase で 1 file 増やすと、作業計画書の肥大を場所を変えて繰り返すことになる
- 本文の 3 条件は、永続化や排他制御が絡む実装を想定した語彙になっている。それらが絡まない Phase (script / 定義 file / 文書だけ) では 1 つ目と 2 つ目が当たらない。その場合は 3 つ目 (完了条件だけで実装形が一意に決まるか) と、未決の判断があるかどうかで判定する
- 判定するのは未決の判断があるかどうかであって、対象 file の数ではない。純粋な rename や一律の型の置換は、10 file に及んでも判断が無ければ省略する。逆に 1 file でも問い合わせの条件や TX 境界に選択肢があれば作る
- 保存データの構造変更だけの Phase と、既存の処理の呼び出しだけで完結する Phase はこの条件に当たることが多い

## Step 1: scope と repo 規範の読み方

- 2 節に分かれた作業計画書: 1 つの Phase を「PR 分割計画」と「実装計画」の 2 節に分けているときは、`grep -n "^### Phase <n>" <作業計画書>` で「実装計画」側の同じ Phase を探し、両方を合わせて scope とする
- repo 規範の取得: 「実装への指針」に列挙が無ければ、設定 file の `rules` に並べた file (未記入なら repo の `.claude/rules/` の file) から、この Phase の対象に当たるものを探す
- 読む上限が 3 file の理由: 全部読むと Phase 1 つの詳細設計に見合わない。この Phase の判断に当たるものを優先して読む。TX の判断なら永続化の rule、排他なら並行制御の rule、命名なら言語の rule が当たる。命名 / 型 / 層 / error / test の制約は、この Step で読んだ rule が正本になる

## Step 2: 調査の細則

### code 解析 tool が使えないとき

Serena などの code 解析 tool が無いか使えないときは、`git grep -n` で定義行を探して調べ、「code 解析 tool が無いため grep で調査した」と成果物に 1 行注記する。

### 保存データの意味が変わるときの洗い出し

対象は、行や状態の意味が変わる変更になる。物理削除から論理削除への切り替え、状態の値の追加、既存の列の意味の変更が当たる。その保存先 (table 等) を読む処理を全部洗い出す。

0. 全 Phase で、意味が変わる table があるかを確かめ、`意味が変わる table: <table 名 (カンマ区切り)>` か `意味が変わる table: なし` の 1 行を Phase 名の直後に記載する。`phase-gate.sh` はこの行が無いと FAIL にし、`なし` なら以降の判定をしない
1. table ごとに `bash "${CLAUDE_PLUGIN_ROOT}/scripts/table-readers.sh" <repo の root> <table 名>` を実行し、この script で拾えない読み取り経路は grep で補う。別の package や管理画面、batch の処理も含める
2. 結果を「実装メモ」の下の `### table を読む query` の節に、`table: <table 名>` の行に続けて記載する。script の出力は末尾の「合計 n 件」も含めてそのまま記載する。見出し名は `phase-gate.sh` が検出するので変えない
3. 洗い出した処理ごとに、意味が変わった行をその処理がどう扱うべきかを判断する。`- 扱い: 変更する (根拠 1 文)` か `- 扱い: 変更しない (根拠 1 文)` の行を、処理の件数と同じかそれ以上の行数で記載する
   - 行は `- 扱い:` で始め、根拠は括弧で囲む。処理の名前は根拠の文の中に記載する。この形でない行は数えない
   - 論理削除への切り替えでは、同じ key で複数行を返し得るかを根拠に記載する (最新 1 件だけを対象にする / 全行を対象にする / 1 件以下が保証される)。以前の形 `- 複数行の扱い: <この 3 つのどれか> (根拠)` も数える
4. Design Doc が有効な行を 1 件以下と決めていても、その担保が登録経路のロックだけなら、読み取りは 2 件を返し得る
5. 「変更する」と判断した処理、つまり条件の追加が必要なものは変更対象 file に含める。この Phase で扱わないものは作業計画書の対象外に記載する
6. `phase-gate.sh` が、宣言の欠落・件数の不一致・扱いの行の不足を FAIL にする

### 既存の担保の特定

作業計画書 / Design Doc が名指しする既存の担保 (ロック / TX 境界 / 一意・外部キー・NOT NULL 等の制約 / 状態遷移) は、その担保を取ると書かれた処理の入口から呼び出し順に確認して特定する。

- 担保の語の grep の hit や file 名の一致で特定しない。同じ語を含む file が複数あると、別機能の担保を根拠にしたまま「記述と実物が一致しない」と判定することになる
- 確認した経路は `<入口の file:line> から <担保の file:line>` の形で 1 行記載する

### 集めた事実の扱い

- 集めた事実は成果物の独立節にしない。実装の判断を変えるものだけを Step 3 の該当項目の下位の箇条書きに記載する。schema の列挙や呼び出し件数は、判断を変えないなら書かない
- **調査は AI が行ってよいが、結果の責任は実装担当者が負う**。返した method 一覧と件数は、採用する前に user が確認する前提で記載する。「AI が調べたから正しい」とはしない

## Step 3: 項目ごとの決め方

### 受け入れ条件の担い手

作業計画書の完了条件が受け入れ条件を引用しているときだけ記載する。条件 1 行につき担い手 (型 / 操作) を 1 つ書く。担い手が決まらない条件は実装形がまだ足りていないので、空欄のまま進めず Step 2 の調査へ戻る。

### 公開する契約の名前

- 新設 / 既存の内部実装を変える / 既存の呼び出しを変える のどれに当たるかを記載する
- 名前は次に従う。これらの指針は Step 1 の 3 file 上限に数えない
  - Step 1 の repo 規範
  - `${CLAUDE_PLUGIN_ROOT}/skills/implement/code-quality.md` 「Naming Criteria」の 3 基準と「Naming Shape」 (repo の語 / 平易な英語 / 削れる語は削る)
  - plugin の `guidelines/languages/` にある対象言語の開発指針
- 根拠にした rule file 名と、基準 1 で数えた先例の件数を 1 行添える
- 本文には何をする method かを言葉で記載し、名前と根拠は「実装メモ」の表に記載する

### 重複や不整合を防ぐ仕組みを替えるとき

例: 一意制約をやめて行ロックで防ぐ。

1. 古い仕組みを前提にした code を列挙する。重複時の読み直し、競合の応答、失敗時の後始末が典型になる
2. 新しい仕組みの下でその分岐に到達する入力があるかを 1 件ずつ判定する
3. 到達しないものは削除する対象にする。旧経路と新経路が code 上で並存する置き換えの Phase では、切り替えと同じ PR で削除すると切り戻せなくなるので、削除は `/specramo:plan --update` で削除の PR 群に追加する (plan の `phase-anatomy.md` 「リリース後の削除の PR 群」)。置き換えを伴わない Phase だけ、この Phase の diff で削除してよい。到達する入力を 1 つも挙げられない分岐を、仮決定として記録しておかない

### API の応答を増減させるとき

status code / error の理由 / field を増減させるときは、その応答を記述した API 仕様 (API の注釈、仕様 file、そこから生成する型) を変更対象 file に含める。再生成の command があれば「実装メモ」に記載する。

### 契約 (型か公開する操作を新しく作るとき)

- 次の 3 つを 1 行ずつ書き、それぞれをどこで守るか (constructor / factory / 業務処理の層 / DB の制約) を添える
  - **不変条件**: インスタンスが成立している間ずっと満たす条件
  - **事前条件**: 呼び出し側が満たす条件
  - **事後条件**: 正常終了時に提供側が保証すること
- 単独の値の範囲は型の内側で守れる。2 つの値の関係 (割引が元の価格を超えない等) と複数レコードの整合性は型の内側だけでは守れないので、守る場所を分けて書く

### テスト観点

- **fixture 条件**: fixture / test data を新規作成するなら、作業計画書の完了条件が引用する条件の数だけ区別できる行 (依頼 / レコード) を列挙する。複数の条件を同じ行で確かめるなら、それが区別不能な状態 (例: DB 上は同じ「対応する行が無い」状態になる) であることを理由として記載する。条件の数より行が少ないまま「fixture を 1 本追加する」とだけ記載すると、実装者はその記述だけでは完了条件を満たす test を作れない
- **扱いを検証する fixture**: 「table を読む query」で「扱い: 変更する」と決めた処理ごとに、意味が変わった行を含む fixture と、その行の扱いが結果に反映される test を記載する。意味が変わった行を含まない fixture だけでは、条件が無い処理でも test が成功する。論理削除で「最新 1 件だけを対象にする」と決めた処理なら、同じ key で有効な行が 2 件ある fixture を置く。状態の値を追加して集計の分類を変えると決めた処理なら、追加した状態の行を含む fixture を置く
- **mutation check**: 契約を記載した Phase では、3 条件のそれぞれに対応する test を 1 つずつ指す (1 対 1 で対応しないものは、その理由を 1 行記載する)

### 図の置き方

- 同じデータの新旧 2 行など、観測できる場面を中心にする
- 箱の label は「1件取得」「管理画面の件数」のように場面名にし、操作名と問い合わせの方針は「実装メモ」の表に記載する。関数名と問い合わせの条件を箱に記載した図は読み手が読み取れない
- 経路の分岐が 3 本以上でも、操作名と問い合わせを箱に記載した図は置かない

## Step 4: 出力の細則

- 本文と「実装メモ」の分け方: 本文に識別子が並ぶと、読み手は判断より先に名前を読み解くことになり、判断が伝わらない。code comment の文面も書かない (実装時に決める)
- 分量: 100 行程度は上限ではない。超えるときは判断の無い節が残存していないかを 1 度確認し、削るものが無ければ超えてよい。目安を大きく超えるときは Phase 自体の大きさを疑い、`/specramo:plan --update` で Phase を割るかを検討する
- 出力先を変えない理由: `/specramo:explain` と `/specramo:implement` は作業計画書と同じ dir だけを検索する
- `phase-gate.sh` が FAIL にする条件: `意味が変わる table:` の宣言が無い / 宣言した table の「table を読む query」の節か `table:` の行が無い / 節の件数が改めて数えた件数と合わない / query ごとの「扱い」の行が足りない

## 禁止事項の理由

- 件数を複製しない理由: 複製した数は作業計画書の更新を反映せず、既存 PR の実装とも一致しない。必要なときは作業計画書の節名で参照し、実装の判断に数が必要なら実物を再度数えて、数えた対象を 1 行記載する
- 「未決」の判定: 作業計画書 / Design Doc の記述と実物が一致しないと判定したときは、記載する前に、根拠にした箇所が対象の経路の内側にあるかを確認する
