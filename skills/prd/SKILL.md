# /specramo:prd - PRD を作る

何を実現したいかを、実装に入る前に 1 つの文書にまとめる。複数の専門の観点から、要件の抜けを見つける。

進め方の全体は次のとおり。小さな修正にはこの手順を使わず、直接実装する。

1. `/specramo:prd` (1 回)
2. `/specramo:design` (1 回)
3. `/specramo:plan` (1 回)
4. Phase ごとに `/specramo:phase-design`、`/specramo:explain`、`/specramo:implement`、`/specramo:review`、`/specramo:explain` の順に進め、PR を作る

## Step 0: 前提確認と雛形の解決

1. 次の command を実行する。終了コードが 2 なら、表示をそのまま利用者に示して止まる。成果物は作らない。

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/require-config.sh"
   ```

2. 雛形の path を決め、その file を読む。

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/resolve-template.sh" prd
   ```

3. 書き出し先を決める。設定 file の `specs_dir` の下に機能名の dir を作り、`prd.md` に書き出す。機能名は引数から決め、無ければ 1 問だけ聞く。同じ path に PRD がすでにあれば、新規ではなく更新として扱う (Step 1 の更新 mode)。

## Step 1: 入力の解釈

| 判定 | 条件 | 動作 |
| --- | --- | --- |
| 更新 mode | `直して` `更新` `書き直し` を含む、または Step 0 の path に PRD がある | 既存の 1.5 節を読み、足りない所と古い所だけを修正する |
| 範囲の限定 | 引数に Q1〜Q5 のどれかを指す語がある | Step 3 でその Q だけを再評価する |
| 新規 mode | 上のどれでもない | Step 2 の聞き取りから始める |

Q の語: Q1 = 目的 / なぜ、Q2 = 作らない / 機会損失、Q3 = 代替案 / OSS / SaaS / 比較、Q4 = 失敗 / リスク、Q5 = 前提 / 成り立たなくなる条件。

## Step 2: 聞き取り

次の 5 つを 1 問ずつ聞く。引数やこれまでの会話に答えがある問いは聞かない。

1. 何を実現したいか (新機能 / 既存の改善 / 不具合の修正)
2. どのサービスが関わるか (repo の code から候補を示す)
3. 外部 API や依存があるか
4. 主な利用者は誰か
5. 主な流れを順に説明してもらう

答えが「不明」「未定」なら、PRD の未決事項に追加して先へ進む。

複雑な要件 (状態が多い、業務ルールが絡む) では、形式化するかを 1 問だけ聞く。必要なら次の 4 つを 4.5 節に記載する。

- 用語
- エンティティ
- 状態遷移の表。今の状態と起きる事象の組ごとに、次の状態と遷移の条件を並べる
- 例外と境界

## Step 3: 判断の質の点検 (省略しない)

同梱した `decision-quality.md` の Q1〜Q5 を当て、結果を PRD の 1.5 節に記載する。NG pattern に当たれば Critical とし、利用者に再度確認する。

## Step 4: PRD の下書き

1. 本文の前に見出しを決め、見出しごとに「その節が所有する主張」を 1 行で決める。結論を置く節は 1 つにし、概要では言い換えて繰り返さない。
2. 雛形の節構成で本文を記載する。受け入れ条件には ID を振らず、「〜のとき、〜が〜になる」の判定できる文にする。
3. 今回作らないものは 1.6 節に集め、他の節からは参照だけにする。
4. 入力が実装方式 (追加する列 / 制約の張り方 / SQL / 使う DB の機能) を指定していても、要件 (非機能要件を含む) と受け入れ条件には業務上保たれる条件 (例: 有効な行は 1 注文につき 1 件) だけを記載する。「DB の制約で防ぐ」「アプリ側で防ぐ」のような、条件を守る場所の指定も実装方式に含める。実装方式は「起票時の実装案」として未決事項に記載し、Design Doc で repo の先例と比べて決める。PRD の要件に実装方式が含まれていると、Design Doc はそれを要件として受け取り、他の案と比べない。

## Step 5: 11 観点のレビュー

| 観点 | 確認すること | 観点 | 確認すること |
| --- | --- | --- | --- |
| SEC | 認証、暗号化、不正な入力の混入 | UX | エラーの表示、待ち時間の表示 |
| PERF | N+1、ボトルネック、キャッシュ | DATA | 履歴、監査ログ、整合性 |
| SRE | 1 か所の障害で全体が止まる箇所、障害の検知、切り戻し | BIZ | 費用と効果、優先度、MVP |
| QA | 境界値、エッジケース | LEGAL | 個人情報、保存期間 |
| ARCH | 依存、拡張性 | EXT | 代替手段、再試行 |
| CUST | 顧客にとっての価値、他の手段から乗り換える理由 | — | — |

各観点の判定を Clear / Partial / Missing で記録する。指摘が無かった観点も記録する。Missing は Step 6 の一覧に「観点が未適用」として載せ、適用しなかった観点が一覧から消えないようにする。

## Step 6: 指摘の一覧

指摘を 3 段階に分けて並べる。

- Critical: 必ず修正する
- Warning: 修正を推奨する
- Info: 検討する

## Step 7: 文章の自己点検

書き出す前に、次の 5 項目を PRD に当てる。当たった箇所だけを書き換え、事実・因果・主体は変えない。

1. 各節の最初の文が、その節の結論になっている
2. 1 文に論点が 1 つだけある
3. 「適切に」「必要に応じて」「柔軟に」のような、判定できない語を使っていない
4. 同じ対象を、節ごとに別の語で呼んでいない
5. 入力や確かめた資料に無い数値・事例・理由を作っていない

## Step 8: 書き出しと承認

1. Step 0 で決めた path に書き出す。
2. Critical の一覧を示し、修正するか承認するかを利用者に聞く。
3. 承認されたら、次のコマンドとして `/specramo:design` を案内する。

## 失敗時の扱い

- 外部 API の仕様を取得できない: 「外部 API の仕様を未取得」を Critical に記録し、仕様の URL を利用者に聞く
- 関わるサービスを code から特定できない: 推測せず、サービス名を利用者に聞く

## 注意

- 共有される文書に、個人の手元の path (`/Users/<名前>/...` など) を記載しない。
- この skill は PRD を作るだけで、実装はしない。
