# PRD の雛形

`/specramo:prd` が使う雛形。導入先の `.specramo/templates/prd.md` に同じ名前の file を置くと、この雛形の代わりに使われる。

```markdown
# PRD: [機能名]

## 1. Overview (目的 / 背景 / 範囲。範囲は「対象範囲」の 1 行で、利用者が触る画面と client を名前で並べ、変更しない client も理由を添えて書く)

## 1.1 用語 (要件と受け入れ条件で使う語を「用語 / 説明」の表で定義する。判定に使う集合 (「抽選済み」に何が含まれるか) と、既存機能の名前を含める。Design Doc の用語節はこの表を参照し、無い語だけを追加する)

## 1.5 判断の根拠 (Q1〜Q5 を 1 行ずつの箇条書きにする: 目的 / 作らない場合 / 採らなかった代替案 / 失敗の想定 / 前提。表と段落にしない)

## 1.6 Non-Goals (今回作らないものを 1 行ずつ、理由を添えて並べる。Q2 と 1. の範囲で対象外にしたものをここに集約し、他の節では参照だけにする)

## 2. Users (対象 / ユーザーストーリー / 役割)

## 3. Functional Req (状態遷移 / 業務ルール)

## 3.5 Formalization (複雑な要件のときだけ)

## 4. Non-functional Req

## 5. Acceptance Criteria (「No / 場面 / 条件」の表。No は読みやすさのための通し番号で、条件に AC-1 のような ID を振らない。「〜のとき、〜が〜になる」の判定できる文にし、後続のステップからは条件の文を装飾せずに引用して指す)

## 6. Open Questions (「No / 事項 / 推奨 / 確認先」の表。PM / 運営 / チームが決める要件側の問いだけを記載する。実装方式の候補は技術メモに置く)
```

節の構成と名前は上のまま使い、Design Doc に合わせない。書き方は次に従う。

- 段落を作らず、入れ子の箇条書きにする
- 主語 (ユーザー / 運営 / サーバ / 画面) と対象を省かない
- **抽選済み** のような状態語は太字にする
- 最上位の節の間に `---` を置く

受け入れ条件は、次の 2 つをすべて覆う。

- 機能要件の各ルールに、そのルールを判定する条件が 1 件以上ある (「(仮)」付きの動作も、仮のまま条件にする)
- 対象範囲に挙げた画面と、同じ操作を呼ぶ別の入口 (例: 詳細画面とは別の画面から同じ操作を実行する部品) のそれぞれに、条件が 1 件以上ある

技術メモ (`tech-notes.md`) は PRD と同じ dir に置き、節を固定しない。
