# Design Doc (spec 型) template

`/specramo:design` が使う雛形。実装から逆算し、受け入れ条件 (ID を振らない表) を軸に本文を組む。書き方の規範は `/specramo:design` の skill に同梱した規範の抜粋が正本。導入先の `.specramo/templates/design.md` に同じ名前の file を置くと、この雛形の代わりに使われる。

## 節構成 (この順で並べる)

記載することが無い節は作らない (「該当なし」の節は置かない)。

```markdown
# Design Doc: [機能名 (merge 後に user か運用者ができること)]

- Status: draft
- Created: YYYY-MM-DD
- Issue / PRD: #XXXX / [PRD path]

> **正本の注記** (後から修正するときはここに日付付きで書き、本文は書き換えない)
>
> なし

## 1. 何を実現するか
[PRD があれば「PRD 「概要」 のとおり」+ PRD から変えた点だけ。無ければ user の言葉で 2-3 文]
[この DD で決める範囲を 1-2 文で書く (例: API の境界、整合性の制約、同時実行時の振る舞い、表示判定、後方互換)。レビュアーが「この DD で見るものは何か」を最初に掴める]

## 2. 用語
[PRD の用語表への link を 1 行置き、ここに書くのは PRD に無い語と、判定に使う集合 (「配送依頼済み」に何が含まれるか) だけ。PRD と同じ定義を書き換えない。行為者 (運営 / ユーザー / サーバ / 画面) の定義は PRD に無ければ 1 行入れる]
- [用語]: [1 行の定義。判定に使う集合は含める要素と含めない要素を書く]

## 3. 現状
### 3.1 現状スナップショット (branch、日付)
| 項目 | 状態 |  ← 数値で書けるものは数値 (件数 / 行数 / 比率)。未計測は【未確定 Qn】
### 3.2 データの関係 (既存 schema があるとき。現状の関係だけを描き、新規 table はここに入れない)
### 3.3 解決する問題 (PRD に課題の節があれば省く)
### 3.4 参考にした既存実装
- [既存の処理]。[新しい処理をその隣に置く / 形を合わせる 等の使い方]

## 4. Implementation Surface (何をどのくらい作るか。PR 分割できる粒度のシステム変更面)
冒頭に合計を 1 行書く (例: API 変更 5 本 (Read 3 / Write 2)、Read の能力 1、DB 新規 table 2 / 列追加 1、画面 4。CLI や library なら 例: subcommand 新規 1、公開関数の追加 2、設定 key 追加 1)。**作るものに合う表だけを置く**: Web API が無ければ Backend API 表を、画面が無ければ Frontend 表を作らず、合計 1 行にも API と画面の数を書かない (`dd-gate.sh` は表も数も無い項目を「対象なし」で PASS にする)。API と画面のどちらも無い変更では合計 1 行も省いてよい。CLI の subcommand、library の公開 API、event / message、batch job、設定 file の key のような外部 interface は Interfaces 表に書く。`Read n / Write n` は Backend API 表の種別列の内訳を指し、能力の表の行数は「Read の能力 n」のように別の語で書いて API の内訳より後ろに並べる (`dd-gate.sh` は最初に現れた `Read n` を採用する)。下の見出し名と 1 列目の header は言い換えずにそのまま使う (`dd-gate.sh` がこの文字列で表を特定する)。Frontend 表の行は変更がある画面だけにし、画面の変更が無いときは表を作らず、合計 1 行には「画面 0」と書くか画面の数を書かない (Data Schema の「保存データの変更なし」と違い、「変更なし」の行を追加すると合計と行数が食い違う)。行の名前は endpoint (`GET /v2/...`) と画面名の具体名で書く。endpoint は route 定義で実在と形 (1 件取得 / 一覧) を確かめ、無ければ「新規」と書く。method 名・SQL・file 名は書かない。field の詳細は Appendix B へ
### Backend API
| endpoint | 種別 (Read / Write) | 変更 (新規 / 既存拡張) | 主な責務 |
### Required Read Capabilities
| Read | 新規 / 既存 | 用途 |
### Required Write Capabilities
| Write | 新規 / 既存 | 条件・結果 |
### Frontend
| 画面 | 種別 (新規 / 更新) | FE 側の logic (表示するだけ / 状態や制御がある) |
### Interfaces (Web API と画面以外の外部 interface があるときだけ)
| interface | 種類 (CLI / 公開 API / event / batch / 設定 等) | 変更 (新規 / 既存拡張) | 主な責務 |
### Data Schema (永続化するデータの設計。RDB 以外 (file / KVS / document DB) なら table を保存単位に読み替える。永続化が無ければ「保存データの変更なし」1 行)
新規の保存単位と既存の保存単位への項目追加を、保存単位ごとに書く (RDB なら新規 table と既存 table の列追加)。「別 table にするか列を追加するか」「一意制約の範囲」は利用者から見える動きを変える決定なので DD で固める。DDL 全文と SQL、migration 手順は書かない (table ごとの 5 列表にそろえる)
| 保存単位 (table / file / key 等) | 変更 (新規 / 項目追加) | 用途 |
RDB のときは、変更後の関係を ER 図 (mermaid `erDiagram`) で 1 つ描く。新規 table と列追加する既存 table、それらが参照する既存 table だけを載せ、新規は entity 名の後に「新規」と書く。線は FK と多重度 (1 対 0..1 / 1 対 0..N) を表し、列は主キーと FK 列だけ書く (5 列表と二重にしない)。`<details>` に入れず本文に置く (判断に必要な図のため)
#### [保存単位の名前] (新規 / 項目追加)
| 項目 (RDB ならカラム名) | 型 | 必須か (RDB なら NULL) | デフォルト | 説明 |
- 先例: [同じ役割の列 / 制約の repo 内の件数と採用 (例: 無効化 disabled_at 3 件 / flag 0 件 → disabled_at を採用。外れるなら理由)]
- index / 制約: [UNIQUE の範囲、FK、index の列を 箇条書き で。同じ親の中で重複を許さない列の組 (表示名 / 表示順 / 識別子) を必ず書き、許すならその理由を書く]
- 不変条件の担い手 (既存の制約 UNIQUE / FK / NOT NULL / CHECK / 排他制御を削除または緩めるときだけ): [何を守るか / 今どの仕組みが守るか / 削除・緩和する制約が防いでいた場面 / 削除・緩和した後の担い手 / 確かめた箇所 の 5 列表。「確かめた箇所」には、削除・緩和した後の担い手が実際にその不変条件を守ることを確かめた code の位置を記載する。ロックやトランザクション、読み取りの条件の位置が当たる。守る仕組みが見つからなければ「なし」と記載する。「削除・緩和した後の担い手」が別 PR になるなら、その間の保険 (読み取り側での対応 等) を Release の節に記載する]
  - 制約を削除するか緩めるときは、上の先例を「現在 n 件 / 撤回 m 件」の形で数える。撤回は、後の変更が制約を削除して別の形に置き換えたもの。`dd-gate.sh` の invariant-owner / invariant-precedent が、担い手の表と先例の件数を判定する
  - 同時に実行される書き込みどうしの競合を防いでいた制約 (一意性 / FK / CHECK 等) を削除・緩和するときは、「確かめた箇所」に、競合する書き込みの経路がどのロック (`SELECT ... FOR UPDATE`、同じ行への UPDATE 等) で直列化されているかを記載する。例は、一意性なら重複する登録、FK なら親の削除と子の登録、CHECK なら不正な状態を作る 2 つの更新。直列化する仕組みが無ければ「なし」とし、同じ業務キー (親の行) をロックする既存のトランザクションの有無と位置を併記する (書き込みをそのトランザクションの内側で実行する案の材料にする)

## 5. 受け入れ条件
[PRD があるとき] PRD 「受け入れ条件」 は全て満たす、と 1 行で引き受け、PRD の条件には 新たに ID を割り振らない (PRD の番号 U-n / A-n 等で参照する)。ここに書くのは PRD に無い条件だけで、2 群に分ける。表の先頭に `No` 列 (1, 2, 3 の通し番号) を置いてよいが (列名を `#` にしない。番号が issue への参照と紛らわしくなる)、読みやすさのためだけで、本文の見出し / 決定事項 / 後続の command からは番号でなく条件の文で指す### 5.1 PRD に書き戻す要件: user か運営から見える振る舞いを決めたもの (PRD の要件の変更、UX の決め、古い client の扱い、表示の欠けの補完)。「PRD A-n を変更 / PRD U-n に追加」と書き、PRD author の確認を経て PRD の更新 PR で反映する。反映後は PRD の番号で参照してここから消す
### 5.2 DD が持つ境界: データの整合や API の設計から出る不変条件 (指定しないときの値、UNIQUE 制約の帰結、再送の冪等性、記録が無いときの整合表示)。PRD author の判断を要しない。次の 3 つは毎回問い、条件になるものだけ表へ追加する (該当しなければ書かない) (抜けると実装の後半に PR が増える): (a) 既に参照されている master 行の変更 (無効化 / 名前変更 / 削除 / 並べ替え) を許すか、許すなら参照側の表示はどう変わるか (b) 同じ内容の再送は書き込まずに成功にするか (c) 切替 (要否 / 有効無効) の逆方向を許すか、許さないなら理由
[PRD が無いとき] | No | 由来 (R-n) | 条件 | の表。条件は [誰が] [何をすると]、[何が] [どうなる]
  - 境界: [0 件 / 上限 / 同時実行 / 再送 / 参照済み行の変更 / 切替の逆方向 のときの結果]
  - 失敗時: [何が起きて user に何が見えるか]

## 6. 振る舞い (順序か分岐がある場面だけ。受け入れ条件の表を読めば分かる場面は節を作らない)
[書くのは、条件の表 1 行では追えない場面に限る: 複数の条件が 1 つの操作の中で順に適用される、経路が 2 つ以上ある (決済失敗と期限切れの戻し処理が別の入口)、同時実行、状態遷移。判定は「図か番号付き手順として書けるか」で、書けない節は条件表の行で足りるので作らない。**この条件に当たる場面では図か番号付き手順を置く (文章だけで説明しない)**。分岐のある受け入れ条件が 2 行以上あるのに節へ図も番号付き手順も無いと、`dd-gate.sh` の `behavior-diagram` が WARN にする。「運営が登録する」「ユーザーが選ぶ」のような正常系の言い直しは書かない]
```

## 外見

- 行数の目安 300 行は本文 (Section 1 〜 Section 12) に当て、用語表 / Implementation Surface の表 / Appendix / `<details>` の図は別枠で数える

- 冒頭は「項目 / 値」の 2 列表 (Status / Created / Last Updated / Related Issue / Related PRD を link で)。その下に正本の注記の blockquote
- 用語は分類ごと (エンティティ / 識別子 / 状態 / 操作・画面) の「用語 / 説明」表にし、本文で使う語を PRD と重複してもすべて記載する。説明は日本語だけで書き、DB 列名や field 名は添えない (列名は Data Schema の 5 列表に置き、用語表には書かない)
- 節名は英語にする (Overview / Glossary / Current State / Implementation Surface / Acceptance Criteria / Proposed Design › Data Flow / Design Decisions / Non-Goals / Deployment and Release Plan / Open Questions / Appendix。Design Judgement は置かず、Review Points は任意)。小節は日本語でよい
- 段落を作らない。節の本文は入れ子の箇条書きで、「前提 → 結果 → 拒否」のような構造を上位と下位の階層で表す。ただし 1 行は日本語の文として読める形にし、記号 (`+` `/` `→`) で語をつないだ句や体言止めの羅列にしない。表の cell も同じで、短い文にする。「現状との差」のような各節の定型行は Current State に集約して繰り返さない- 主語と対象を省かない。「要否を変える」でなく「運営が商品の配送オプションの要否を変える」のように、誰が (ユーザー / 運営 / サーバ / 画面)、何の (商品 / 配送オプション / 注文)、何を、まで書く。抽象的な言い回しでよいが、行為者と対象は具体にする
- 動作の主体をそろえる。サーバや運営が行う動作を、対象物 (サイズ行 / 案内文 / 再依頼) を主語にして書かない (「サイズ行は変更を拒否する」でなく「サイズ行については変更を受け付けない」)。主語を省くなら文書全体をサーバ主語で統一する
- chat の癖語を文書の語に置き換える: 引く → 参照する、決め → 決定 / 動作、扱い → 動作、足す → 追加する、出す → 表示する / 返す、`取り直す` → 再取得する。条件と結果で同じ語を使わない (「確定した時点で…確定せずに」のような衝突)。
- 最上位の節の間に `---` を置く。節をまたぐ参照は `[節名](#anchor)` の link にする
- 受け入れ条件 / 決定事項 / CUD / 未確定は表で書く。**有効** / **無効** のような状態語と「案 A (採用)」は太字にする
- 大きい図 (ER / sequence) と Appendix は `<details><summary>展開して読む (対象)</summary>` で囲む。本文で判断に必要な図 (state / flowchart) は入れない
- 設計判断が 4 つ以下なら Section 7 の表、5 つ以上なら「決定 n」小見出しで本文に記載する。Appendix に比較表を分けない (本文と Appendix で決定が二重になる)
- 表の列幅は repo で使っている markdown の整形 tool があればそれで合わせる (例: `npx prettier --parser markdown`)。無ければ揃えなくてよい

## 図の使い方

- 図を置くのは順序か分岐がある箇所だけ: 同時実行 (sequence)、状態遷移 (state)、リリース手順 (flowchart)、schema の関係 (ER。現状は Section 3.2、変更後は Data Schema)。CUD の条件や決定事項は表のまま
- **該当する箇所では図を置くのが原則で、文章だけの説明に替えない**。図の代わりに番号付き手順を記載してもよい。情報の構造で表現を決める (単純なもの = 表、順序だけ = 番号付き手順、分岐と再結合 = 図)。逆に、該当しない箇所へ図を増やさない (図の作成自体が仕事になる)
- 正常系だけの sequence 図は本文の 箇条書き と同じ情報なので置かない。競合や失敗の分岐がある場面に限る
- mermaid の label に `<br/>` を使わない (描画されない viewer がある)。flowchart の node は 10 文字前後に収め、説明は図の下の 1 段落に記載する。state 図は `state "表示名" as id` と遷移だけで表現し、複合 state の中に説明を記載しない
- 本番の数値 (分布 / 比率) が取れたら Section 3.1 に表かグラフで置き、決定の根拠にする

| 5. 受け入れ条件 | 真偽が判定できる文。境界と失敗時を下位 箇条書き に | 「適切に」「必要に応じて」、実装手順 |
| 6. 振る舞い | 前提 → 結果。現状は実物で確認した挙動 | 識別子 (Appendix へ)、層の話 |
| 7. 決定事項 | 実装者が code を読んでも決められない点 | 関数名 / 層の分け方 / 読み込み済みの再利用 |
| 9. 設計判断 | 仕様の選択肢としての比較 | 「再実行 vs 再利用」のような実装の書き方の比較 |

## 節を削る判定

- 選択肢が無かった機能では 9 を削る。data も画面も増えない変更では 4 の該当行だけ維持する。API も画面も無い変更 (CLI / library / batch / 組み込み) では Backend API と Frontend の表を作らない
- どの受け入れ条件にも対応しない節や表は削る。逆に、どの節にも説明が無い受け入れ条件は 6 に見出しを追加する。対応は書き手が確かめる作業で、本文に番号を記載して示さない
- Appendix の図は、5 と 6 を読んで順序が追えないときだけ追加する (図が無いと読めない doc は本文が不足している)

## /specramo:plan との接続

- `/specramo:plan` は 5 の受け入れ条件を条件の文 (先頭 20 字程度) で引用して Phase へ割り当て、各 Phase の完了条件にどの test で確かめるかを記載する
- Phase の合計が受け入れ条件の総数を過不足なく覆うことを `/specramo:plan` の自己点検で確かめる。覆えないときは Design Doc 側の 5 が不足しているので、`/specramo:design --update <path>` で条件を追加してから戻る
