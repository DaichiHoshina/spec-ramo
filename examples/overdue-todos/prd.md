# PRD: 期限切れ TODO の一覧 (overdue-todos)

## 1. Overview (目的 / 背景 / 範囲)

- **目的**: API の利用者が、対応が遅れている TODO を 1 回の request で識別できるようにする
- **背景**
  - 現在の API は `GET /todos` で全件を返すだけで、条件に合う TODO を抽出する手段が無い
  - 利用者は **期限切れ** かどうかを自分で判定している。同じ判定が利用者の数だけ重複する
  - 判定を API 側の 1 箇所に置くと、**期限なし** と **完了済み** の扱いがすべての利用者で一致する
- **対象範囲**: 新しい endpoint `GET /todos/overdue` を 1 つ追加する。既存の `GET /todos` は変更しない (既存の利用者の読み方を変えないため)。画面は無い

---

## 1.1 用語

| 用語 | 説明 |
| --- | --- |
| 期限 | TODO に設定する日時。設定しないこともできる |
| **期限なし** | 期限を設定していない TODO |
| **完了済み** | 完了の印が付いた TODO |
| **期限切れ** | 期限が設定され、完了しておらず、期限が現在時刻より前の TODO |
| 現在時刻 | 1 回の request の処理の始めに確定した時刻 |
| 全件一覧 | 既存の `GET /todos`。すべての TODO を返す |

---

## 1.5 判断の根拠 (Q1〜Q5)

- **Q1 目的**: 「期限切れとは何か」の判定を API 側の 1 箇所に置き、どの利用者でも同じ結果にする (依頼の「一覧したい」を 2 回掘り下げた結果)
- **Q2 作らない場合**: 利用者が判定を自分で実装し続け、期限なしと完了済みの扱いが利用者ごとに一致しないままになる。作る費用は endpoint 1 つで小さいので、作る
- **Q3 採らなかった代替案**: 全件一覧に抽出の条件を指定できるようにする案 (全件一覧の応答の意味が変わる)、任意の条件で抽出できる汎用の仕組みを作る案 (条件が 1 つの時点で作ると使われない機能が増える)、利用者側の判定を続ける案 (目的を満たさない)
- **Q4 失敗の想定**: 期限ちょうどの TODO の扱いが利用者の想定と違い、問い合わせが来る。並び順を仕様に書かず、利用者が偶然の順序に頼る
- **Q5 前提**: TODO の件数が少なく、1 回の応答で全件を返せる。件数が増えてページングが必要になると、応答の形が変わる

---

## 1.6 Non-Goals

- **ページング**: 件数が少ない前提なので、応答は配列 1 つとする (Q5 の前提が成り立たなくなったら検討する)
- **並び順の指定**: 順序は仕様として 1 つに固定する。利用者が順序を指定する仕組みは作らない
- **期限が近い TODO の一覧**: 依頼の対象は期限を過ぎたものに限る
- **利用者ごとの抽出と認証**: 現在の API に認証が無いので、この変更では扱わない
- **汎用の抽出の仕組み**: Q3 で採らなかった案のため、条件が 1 つの時点では作らない
- **保存先の変更**: 今の保存方式のまま進める
- **全件一覧の応答の変更**: 既存の利用者に影響するので変更しない

---

## 2. Users (対象 / ユーザーストーリー / 役割)

- **対象**: TODO API を呼ぶ利用者 (client)
- **ユーザーストーリー**: 利用者として、期限を過ぎていて完了していない TODO だけを 1 回の request で取得したい。全件を取得して自分で抽出する処理を不要にしたい
- **役割**: 認証が無いので、役割による区別はしない。すべての利用者が同じ結果を受け取る

---

## 3. Functional Req (状態遷移 / 業務ルール)

- **期限切れの判定**: 次の 3 つをすべて満たす TODO を一覧に含める
  - 期限が設定されている
  - 完了していない
  - 期限が現在時刻より前である
- **境界**: 期限が現在時刻とちょうど同じ TODO は含めない (依頼に指定が無かったので推奨で決定した。6. の No 2 で確認する)
- **並び順**: サーバは期限の古い順に並べて返す。期限が同じ TODO の間の順序は決めない
- **該当が 0 件のとき**: サーバは HTTP 200 と空の配列を返す。error にはしない
- **現在時刻**: サーバは 1 回の request の中で現在時刻を 1 度だけ確定し、すべての TODO の判定に同じ時刻を使う
- **全件一覧**: 全件一覧の応答は変更しない

---

## 3.5 Formalization

状態遷移は無いので、判定の組み合わせを表で固定する。

| 期限 | 完了 | 期限と現在時刻の関係 | 一覧に含めるか |
| --- | --- | --- | --- |
| なし | 完了していない | 比べない | 含めない |
| なし | 完了済み | 比べない | 含めない |
| あり | 完了済み | 現在時刻より前 | 含めない |
| あり | 完了済み | 現在時刻と同じか後 | 含めない |
| あり | 完了していない | 現在時刻より前 | **含める** |
| あり | 完了していない | 現在時刻と同じ | 含めない |
| あり | 完了していない | 現在時刻より後 | 含めない |

---

## 4. Non-functional Req

- **応答時間**: 全件一覧と同じ水準にする。数値の目標は現在の API に無いので設定しない
- **判定の置き場所**: 期限切れの判定は API 側の 1 箇所で行う
- **互換性**: 全件一覧の path と応答と Content-Type を変更しない
- **時刻の扱い**: 比較は絶対時刻で行い、timezone の設定で結果が変わらないようにする

---

## 5. Acceptance Criteria

| No | 場面 | 条件 |
| --- | --- | --- |
| 1 | 期限切れの TODO がある | 期限が現在時刻より前で完了していない TODO があるとき、`GET /todos/overdue` の応答にその TODO が含まれる。 |
| 2 | 期限なし | 期限を設定していない TODO は、完了していなくても `GET /todos/overdue` の応答に含まれない。 |
| 3 | 完了済み | 完了済みの TODO は、期限が現在時刻より前でも `GET /todos/overdue` の応答に含まれない。 |
| 4 | 境界 | 期限が現在時刻と同じか現在時刻より後の TODO は、`GET /todos/overdue` の応答に含まれない。 |
| 5 | 0 件 | 該当する TODO が 1 件も無いとき、`GET /todos/overdue` は HTTP 200 と空の JSON 配列 `[]` を返す。 |
| 6 | 並び順 | 期限切れの TODO が複数あるとき、応答の並びは期限の古い順になる。 |
| 7 | 応答形式 | `GET /todos/overdue` の応答の Content-Type は `application/json` になる。 |
| 8 | 全件一覧 | `GET /todos` の応答は、この変更の前後で同じになる。 |
| 9 | 判定の置き場所 | 期限切れの判定が 1 箇所に実装され、handler は判定の条件を自分で組み立てない。 |
