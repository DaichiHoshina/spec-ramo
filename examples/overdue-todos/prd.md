# PRD: 期限切れ TODO の一覧 (overdue-todos)

## 1. Overview (目的 / 背景 / 範囲)

`GET /todos/overdue` を新設し、期限を過ぎていて完了していない TODO だけを返す。

**目的**: API の利用者が、対応が遅れている TODO を 1 回の request で識別できる状態にする。

**背景**: 現状の API は `GET /todos` で全件を返すだけで (`todo/handler.go:11`)、条件による抽出の手段が無い。期限切れかどうかの判定は各 client が実装しているので、同じ判定が client の数だけ重複する。判定を API 側の 1 箇所に置くと、期限なしと完了済みの扱いがすべての client で一致する。

**範囲**: package `todo` に抽出の処理と endpoint を 1 つ追加する。保存方式 (メモリ上の `Store`) と既存の `GET /todos` の応答は変更しない。

## 1.5 判断の根拠 (Q1〜Q5)

### Q1. 本当の目的か (Why を 2 回)

| 段 | 内容 |
| --- | --- |
| 依頼のままの目的 | 期限を過ぎても完了していない TODO を一覧できるようにする |
| Why 1 回目 | 全件を取得してから client 側で抽出する形になっていて、判定が client ごとに重複する |
| Why 2 回目 | 判定が重複すると、期限なしや完了済みの扱いが client ごとに一致しなくなり、同じ問いに API が 1 つの答えを返せない |
| 上位の目的 | 「期限切れとは何か」の判定を API 側の 1 箇所に置き、どの client でも同じ結果になる状態にする |

上位の目的が依頼の文言と別になっているので、目的の掘り下げができている。

未確認の推測: 「client 側で抽出している」は現状の code から読み取れる構造で、実際に複数の client が重複した判定を実装しているかどうかは確かめていない。client が 1 つだけなら、この目的の効果は小さくなる。

### Q2. 「何もしない」を選択肢として評価したか

| 案 | 機会損失 | 維持の費用 |
| --- | --- | --- |
| 何もしない | 利用者は全件取得を続け、期限切れの判定を自分で実装する。判定の定義が API に無いので、期限なしと完了済みの扱いが利用者ごとに一致しないままになる | 0 行。API の endpoint は増えない |
| client 側の抽出を続ける | API 側の変更は不要。全件を転送するので、件数が増えると転送量が件数に比例して増える | client ごとに判定 code を維持する。client が N 個あれば N 箇所 |
| 既存の代替を使う | この repo は外部 library を使っていない (`go.mod` の require が 0 件)。query 用の library や検索基盤を採用すると、20 行程度の抽出処理に対して依存が 1 つ増える | 依存の更新の手間が増える |

**採用の判断**: 作る価値が何もしない価値を上回る。根拠は、判定の定義 (期限なしを含めない / 完了済みを含めない / 現在時刻と比べる) を API 側に固定できる点にある。実装の規模は関数 1 つと endpoint 1 つで、維持の費用は小さい。

### Q3. 代替案を 3 つ以上比べたか

| 案 | 費用 | 期間 | risk | 元に戻しやすさ |
| --- | --- | --- | --- | --- |
| A. 専用 endpoint `GET /todos/overdue` (**採用**) | `Store` に抽出の関数 1 つ、handler に route 1 つ | 小 | 条件が増えるたびに endpoint が増える | route の削除だけで元に戻せる |
| B. `GET /todos?overdue=true` の query parameter | parameter の解析と検査が追加で必要 | 小 | parameter の組み合わせが増えると `GET /todos` の分岐が増える | parameter を無視すれば元に戻せる |
| C. client 側の抽出のまま (API を変更しない) | 0 | 0 | 判定が client ごとに一致しない。API は「期限切れ」を定義しない | 変更が無いので元に戻す対象も無い |
| D. `Store` に汎用の条件を渡す仕組みを作る | 条件を表す型と組み立ての設計が必要 | 中 | 利用者が 1 つの時点で汎用化するので、使われない機能が増える | 型を公開した後は削除しにくい |

**採用した A の優位**: 他案の弱点と A の弱点を並べて比べる。C は判定を API 側に置けないので、今回の目的を満たさない。D は条件が 1 つしか無い時点で抽象化するので、設計の選択肢を早く固定してしまう。B は `GET /todos` の応答の意味が parameter で変わり、既存の利用者の読み方と新しい読み方が 1 つの endpoint に共存する。A の弱点は「条件が増えると endpoint が増える」点だが、条件が 2 つ目に増えた時点で B か D への変更を判断できる。今回の依頼が path を `GET /todos/overdue` と指定している点も A と一致する。

### Q4. 6 か月後に失敗しているとしたら原因は何か (3 件)

| 種別 | 失敗の姿 | 早く気づく手がかり |
| --- | --- | --- |
| 技術 | 保存件数が増え、毎 request で全件を複製してから抽出する形が応答時間を長くする。`Store.List` は全件を新しい slice に複製する (`todo/store.go:23`) | `GET /todos/overdue` の応答時間が `GET /todos` と同じ割合で長くなる |
| 運用 | 現在時刻を関数の内部で直接取得していて、期限ちょうどの境界を test で固定できない。境界の不具合が本番の問い合わせで初めて判明する | 「期限ちょうどの TODO が一覧に含まれるのか」という利用者からの問い合わせが発生する |
| 想定外の使い方 | 利用者が応答の並び順を暗黙に前提にする。仕様に順序を記載しないまま実装の順序に依存され、内部の保存順を変更した時点で利用者側の表示が変わる | 順序を変更する PR の review で「互換性はどうなるか」と指摘される |

### Q5. 前提が成り立たなくなる条件

| 条件 | 影響 | 移行の費用 (概算) |
| --- | --- | --- |
| 保存先がメモリから DB に変わる | 全件を取得してから抽出する形が使えなくなり、条件を SQL 側で表す必要がある | 抽出の関数 1 つの書き換えと、index の検討。関数の呼び出し側は変更せずに済む |
| 認証を追加し、利用者ごとの TODO になる | 一覧が利用者ごとの範囲になり、判定条件に利用者 ID が加わる | 関数の引数の追加と、handler での利用者の特定 |
| 件数が増えてページングが必要になる | 応答が配列 1 つでは足りなくなり、応答の形が変わる | 応答形式の変更で、既存の利用者に影響する |
| 期限の意味が日付単位に変わる (時刻を扱わない運用) | 現在時刻との比較では境界が一致しない。日付の境界で判定する必要があり、timezone の決定が必要になる | 判定条件の書き換えと、timezone の方針の決定 |

## 1.6 Non-Goals (今回作らないもの)

- **ページング**: 件数が小さい前提なので、応答は配列 1 つとする。Q5 の「件数が増える」条件が成り立った時点で検討する。
- **並び順の指定 (query parameter)**: 順序は仕様として 1 つに固定する。利用者が順序を指定する仕組みは作らない。
- **期限が近い TODO の一覧 (期限を過ぎていないもの)**: 依頼の対象は期限を過ぎたものに限る。
- **利用者ごとの抽出と認証**: 現状の API に認証の仕組みが無いので、この変更では扱わない。
- **`Store` の汎用の抽出機構**: Q3 の案 D と同じ内容である。条件が 1 つの時点では作らない。
- **保存先の変更 (DB 化)**: メモリ保存のまま進める。
- **`GET /todos` の応答の変更**: 既存の応答は変更しない。

## 2. Users (対象 / ユーザーストーリー / 役割)

**対象**: TODO API を呼ぶ client。現在この repo に含まれる呼び出し元は test だけで (`todo/handler_test.go`)、外部の client の数は確かめていない。

**ユーザーストーリー**: API の client として、期限を過ぎていて完了していない TODO だけを 1 回の request で取得したい。全件を取得して自分で抽出する処理が client 側で不要になる。

**役割**: 認証が無いので、役割による区別はしない。すべての client が同じ結果を取得する。

## 3. System (依存するサービス / データの流れ / 外部 API)

**依存するサービス**: なし。単一の Go module `example.com/todoapi` の package `todo` だけで完結する。`go.mod` の外部 require は 0 件で、標準 library だけで実装できる。

**データの流れ**:

1. client が `GET /todos/overdue` を呼ぶ。
2. handler が現在時刻を確定する。
3. handler が `Store` から期限切れの TODO を取得する。`Store` は `mu` で保護した slice を走査し、条件に当てはまる TODO だけを集める。
4. handler が結果を期限の古い順に並べ、JSON の配列として返す。

**外部 API**: なし。取得する仕様も無いので、この skill の失敗条件 (外部 API の仕様を未取得) には該当しない。

## 4. Functional Req (判定の rule / 応答)

期限切れの判定は、次の 3 条件をすべて満たすことで表す。

1. 期限が設定されている (`Due` が zero value でない)。`Todo.Due` は zero value を「期限なし」として扱う定義になっている (`todo/todo.go:6`)。
2. 完了していない (`Done` が false)。
3. 期限が現在時刻より前である (`Due.Before(now)` が true)。

**境界の扱い**: 期限が現在時刻とちょうど同じ TODO は含めない。判定を厳密な「より前」に固定し、比較の向きを 1 つに確定させる。依頼に指定が無かったので推奨で決定した (Review Result の Warning に記載)。

**並び順**: 期限の古い順に並べる。対応が遅れている順に利用者が読める状態になる。期限が同じ TODO の間の順序は決めない。

**該当が 0 件のとき**: HTTP 200 と空の JSON 配列 `[]` を返す。JSON が `null` にならないようにする。

**現在時刻の取得**: 判定に使う現在時刻は、1 回の request の中で 1 度だけ確定し、走査の途中で再取得しない。走査中に時刻が進んで判定が一致しなくなる事態を避ける。

**既存の endpoint**: `GET /todos` の応答は変更しない。

## 4.5 Formalization

状態遷移は無いので、遷移の表は作らない。代わりに判定の組み合わせを表で固定する。

**用語**

| 用語 | 定義 |
| --- | --- |
| 期限 | `Todo.Due`。zero value は「期限なし」を表す |
| 期限なし | `Due` が zero value の TODO |
| 完了済み | `Done` が true の TODO |
| 期限切れ | 期限が設定され、完了しておらず、期限が現在時刻より前の TODO |
| 現在時刻 | 1 回の request の処理の始めに確定した時刻 |

**エンティティ**: `Todo` (`ID` / `Title` / `Due` / `Done`) と `Store` (`Todo` の集合)。この変更で field は追加しない。

**判定の組み合わせ**

| 期限 | 完了 | 期限と現在時刻の関係 | 一覧に含めるか |
| --- | --- | --- | --- |
| なし | 完了していない | 比べない | 含めない |
| なし | 完了済み | 比べない | 含めない |
| あり | 完了済み | 現在時刻より前 | 含めない |
| あり | 完了済み | 現在時刻と同じか後 | 含めない |
| あり | 完了していない | 現在時刻より前 | **含める** |
| あり | 完了していない | 現在時刻と同じ | 含めない |
| あり | 完了していない | 現在時刻より後 | 含めない |

**例外と境界**

- 期限が現在時刻とちょうど同じ: 含めない。
- 期限が 1 ナノ秒だけ過去: 含める。`time.Time` の比較は絶対時刻で行われるので、判定は `Due` に付いた timezone の表記に依存しない。
- 該当が 0 件: 空の配列を返す。error にはしない。
- `Store` が空: 空の配列を返す。

## 5. Non-functional Req

- **計算量**: 走査は件数に比例する (O(n))。件数が小さい前提なので index は作らない。
- **応答時間**: メモリ上の走査だけなので、`GET /todos` と同じ水準にする。数値の目標は現状の API に無いので設定しない。
- **並行性**: 判定の間も `Store` の lock で保護し、走査中に slice が書き換わらないようにする。`Store` は `sync.Mutex` で `Add` と `List` を保護している (`todo/store.go:6`)。
- **時刻の扱い**: 比較は絶対時刻で行い、timezone の設定に依存させない。
- **互換性**: 既存の `GET /todos` の path と応答と Content-Type を変更しない。
- **可観測性**: log と metrics の仕組みが現状の repo に無いので、この変更では追加しない。

## 6. Acceptance Criteria

- 期限が現在時刻より前で完了していない TODO があるとき、`GET /todos/overdue` の応答にその TODO が含まれる。
- 期限を設定していない TODO は、完了していなくても `GET /todos/overdue` の応答に含まれない。
- 完了済みの TODO は、期限が現在時刻より前でも `GET /todos/overdue` の応答に含まれない。
- 期限が現在時刻と同じか現在時刻より後の TODO は、`GET /todos/overdue` の応答に含まれない。
- 該当する TODO が 1 件も無いとき、`GET /todos/overdue` は HTTP 200 と空の JSON 配列 `[]` を返す。
- 期限切れの TODO が複数あるとき、応答の並びは期限の古い順になる。
- `GET /todos/overdue` の応答の Content-Type は `application/json` になる。
- `GET /todos` の応答は、この変更の前後で同じになる。
- 期限切れの判定が 1 箇所に実装され、handler は判定の条件を自分で組み立てない。

### 指摘の一覧

**Critical (必ず修正する)**

- なし。

**Warning (修正を推奨する)**

- **期限ちょうどの扱いが依頼に無かった**: 「現在時刻と比べる」だけでは、期限が現在時刻と一致したときの結果が決まらない。推奨で「含めない」と決定し、4 節に記載した。別の扱いを望む場合は、4 節と 4.5 節の表と受け入れ条件を同時に修正する。
- **抽出処理の実装場所**: `Store.List` が全件を複製する実装なので (`todo/store.go:23`)、handler 側で `List` を呼んでから抽出すると、返す件数と無関係に全件の複製が発生する。抽出は `Store` 側の関数に実装し、lock の中で判定する。
- **現在時刻を test で固定できる形にする**: 現在時刻を関数の内部で直接取得すると、期限ちょうどの境界を test で確かめられない。時刻を引数で受け取る形を推奨する。実装の形は `/specramo:design` で決定する。

**Info (検討する)**

- **並び順を仕様として記載するかどうか**: 今回は期限の古い順を仕様とした。順序を決めないままにすると、利用者が実装の順序に依存する (Q4 の 3 件目)。
- **client の数を確かめていない**: この変更の効果は client の数に比例する。repo 内の呼び出し元は test だけだった。
- **期限が近い TODO の一覧との関係**: 条件が 2 つ目に増える段階で、Q3 の案 B (query parameter) か案 D (汎用の条件) への変更を判断する。
